# RockGuard - what was done

## Step 1: pages
- The single-file design (`_original/index.original.html`, an "x-dc" component with 7 screens) is split into one static HTML file per page by `node tools/build-pages.js`:
  `index`, `products`, `resources`, `project-highlights`, `project-highlight` (template of every project), `credit-application`, `contact`, `lunch-learn`.
  Same look, no framework at run time. Interactions (tabs, filters, credit steps, forms, slider, menu) are in `js/site.js`; `css/styles.css` is the original design CSS, `css/site.css` adds the hamburger menu, mobile breakpoints and 1920-4K scaling.
- Images: all design photos are WebP under 100 KB in `images/` (`node tools/make-images.js`; the originals are kept OUTSIDE the project in `D:\projects\ROCKGUARD_images_backup\originals`).
- `tools/original.js` runs the script of the original design in Node (data of products, projects, resources); `build-pages.js` and `seed-content.js` use it.
- `node tools/dev-server.js 5195`: static server + proxy of `/api` and `/admin` to `https://cmsapi.qpaix.com/rockguard/...` (port 5195 because 5190 is used by another project). `vercel.json` has the same rewrites for production.

## Step 2-3: footer, login
- One footer for every page (`tools/footer.html`), CMS Login link in the Company column. `login.html` (split screen, eye button, "I am not a robot" tick) posts to `/api/admin/login`. Favicon = red "RG" square of the design.
- Test admin (LOCAL DB only): `test@rockguard.biz` (Supabase Auth + `rockguard.cms_admins`, role admin). Change or remove before going live.

## Step 4: live editor
- `tools/cms-tag.js` + `tools/cms-keys.json`: every editable text / image / link gets a stable key from what it IS (kind + default text / file), never from its position. Rebuilds keep the keys (commit the registry). Parts drawn from the CMS lists (products, resources, project highlights) are not keyed.
- `js/cms.js` (+ `css/cms.css`, `js/rg-toolbar.js`): admin bar, edit / preview, inline text + image edit, link editor, SAVE via `/api/v2/page-elements`, text format toolbar (works on all editable texts across the whole site: data-cms, repeatable lists data-rs, product fields data-sf, project highlights data-pf, articles data-af, and custom sections).

## Step 5: public pages read the CMS (`js/rg-content.js`)
- Home product cards, Products page (tabs + Accessories), Resources page (product tiles + 6 filters), Project Highlights (list / grid + search) and each project (`/project-highlight-<slug>.html`, rewritten to `project-highlight.html`) are drawn from `/api/v2/solutions`, `/resources`, `/stories`. If the API cannot be reached the shipped content stays.
- Where a product's data lives (the backend has no extra columns): solution row (title, `category` = tag line, `short_description` = summary, `icon_image_url` = card photo, `product_family` = hd / pw / acc) + page elements of the page `product-detail-<slug>`: `prod-lead`, `prod-image`, `prod-tile`, `prod-features` (JSON), `prod-downloads` (JSON), `prod-acc-desc`. Project extras are JSON in `result_text`; a resource's product is `[product:<slug>]` in its description.
- `tools/seed-content.js` (`RG_PASS=... node tools/seed-content.js`, `--dry-run`): seeded the LOCAL DB with the content of the design: 4 solutions (RockGuard HD, PipeWeights, RockGuard Tape, PipeWeights Hoppers), 2 projects (Bayou Bridge, Shin Oak), 12 resources. Nothing invented; PDF links still point to rockguard.biz.

## Step 6: solution template page, add / remove on the whole website
- **Solution template** (`solution-reference.html`, route `/product-detail-<slug>.html` in `vercel.json` + dev server): every solution created in the Dashboard gets its own page (the backend already sets this link). `js/rg-content.js` (`solutionRef`) draws it from the solution row + the page elements `prod-*` of `product-detail-<slug>`: hero, photo, tag line, lead text, Get a Quote / Data Sheet buttons, Features & Benefits cards, Downloads. In edit mode every text, the photo, the features (+ Add / remove) and the downloads (+ Add / remove, link or upload a file) are editable; SAVE writes the solution row (title, tag line, summary) and the page elements (and the change history).
- **Add / remove everywhere** (`js/rg-sections.js`, markers set by `tools/build-pages.js`):
  - Repeatable lists (`data-rlist`): home stats + about paragraphs, Lunch & Learn questions, contact offices, credit terms / guaranty / sale terms, footer Products + Company link columns (the CMS Login link stays). Edit mode: edit items, remove (x), "+ Add item" (clone of the last item), change photo / link; SAVE stores one JSON page element per list (`rl-<page>-<name>`, footer lists `g-rl-footer-*` are shared by all pages).
  - Sections: adding / removing whole sections was switched off later (2026-10-24, on request): no "Remove section" / "Add section here" controls, a saved `sec-config` is ignored (flag `SECTIONS_EDITABLE` in `js/rg-sections.js`). Only the items of the lists can be added / removed.
  - Header menu labels and footer headings / copyright are CMS texts too (`g-txt-*`, `g-footer-*`, shared by all pages).
- Not in the live editor (they are CMS lists, managed in the Dashboard / next step): products on the Products page, resources, project highlights, and the 15 home gallery photos (each photo can be replaced).

## Step 7: dashboard (`dashboard.html`, `js/dashboard.js`, `css/dashboard.css`)
- Sidebar: Overview, **Solutions**, **Project Highlights**, **Resources**, Settings (Change History, Email Configuration, Change Password) and, for admins only, **Pending Approvals** and **Team & Access**. Opens by itself inside the live site from the DASHBOARD button (`dashboard.html?embed=1`, the page reloads when it is closed after a change). The edit-mode pages get "Edit ... in the Dashboard" badges on the lists drawn from the CMS.
- **Solutions** (add / edit / delete): name, small heading, order, group (RockGuard HD / PipeWeights / Accessory / Other), summary (home card), lead text, card photo, product-page photo, Resources-tile photo, features (`Title | text` per line), downloads (`Label | link | type` per line), page the card opens, show / hide. The product page texts are saved as the page elements `prod-*` of `product-detail-<slug>`; a new solution gets its own page `/product-detail-<slug>.html` from the template.
- **Project Highlights**: title, page heading, location, dates, owner, contractor, supplier, product, benefits, card text, challenge, solution, up to 6 photos, project PDF / link. The extras are kept in `result_text` (JSON; the fields the form does not show, e.g. the technical table, are kept).
- **Resources**: title, type (Data Sheet, Sizing Chart, Installation, Brochure, Specification, Safety, Technical Note, Webinar, Video, Blog Post), product (= a solution), file or link, show / hide; type tabs like the Resources page + a product filter with counts; "Add" starts with the selected tab's type and product.
- **Change Password**, **Email Configuration** (SMTP + CC rows per form: Contact, Lunch & Learn, Credit Application + send a test mail), **Change History** (dashboard saves, live-editor saves, list / section edits), **Team & Access** (add admin / editor, edit, reset password, remove) and **Pending Approvals** (an editor's saves wait there; approve / reject), same backend endpoints as the other CMS sites. Every dashboard save is written to the change history.
- Blog / Webinar pages of their own do not exist on this website (their resources open the file / link), so the template pages for them were not made.

## Reference (template) pages: blog, webinar, project highlight, solution
A new item made in the Dashboard gets its own page at once, drawn from the template of its kind (`vercel.json` rewrites, emulated by `tools/dev-server.js`; `?slug=` works too; a real file always wins):
| Dashboard item | Address | Template |
|---|---|---|
| Solution | `/product-detail-<slug>.html` | `solution-reference.html` |
| Project Highlight | `/project-highlight-<slug>.html` | `project-highlight.html` |
| Resource, type Blog Post | `/blog-<title>.html` | `blog-details.html` |
| Resource, type Webinar | `/webinar-<title>.html` | `webinar-details.html` |
- **Blog / Webinar** (`js/rg-content.js` `articleRef`): hero with the cover photo, formatted text (short first line = sub-heading, lines starting with - / • = numbered cards, `[image: url | caption]` = picture, blank line = new paragraph), side card (product, date, reading time / questions phone, "More about <product>" or "Watch / Register"), contact band. The text of the page is stored in the resource description after a line `[page]` (the short description stays before it). Resource cards of these types open their own page (READ / WATCH).
- **Inline editing on every template page** (edit mode): solution (texts, photo, features, downloads), project highlight (heading, location, owner, product, benefits add / remove, photos change / add / remove, PDF link, challenge / solution text), blog / webinar (title, text, cover photo, "Insert image in the text"). SAVE writes the CMS item + change history (editors go to approval).
- Dashboard > Resources: short description, "Text of its own page" (Blog Post / Webinar), cover photo, and a Page column with the address of the page.

## Step 8: forms send mail
- `js/site.js`: Contact, Lunch & Learn and the six-step Credit Application post to `/api/contact` (`form_type` `support` / `lunch_learn` / `credit_application`; all fields of the credit form). The backend mails them through the SMTP account of Dashboard > Email Configuration and copies the CC rows of that form. The "sent" screen shows only after the mail went out; on a failure an error is shown under the button and the form keeps its data. The CC rules of the Dashboard compare codes (country `US`, state `TX`): `js/geo.js` (generated) holds the name -> code tables and the country / state of the forms are converted before sending.

## Step 9: page loader + browser data cache
- Every public page shows a loader (the website logo: the header shield on a glass disc with a red progress arc, a slowly turning tick ring and radar pulses + the colour RockGuardHD wordmark on the light site colours; a faint diamond mesh drifts behind and a thin red progress line runs along the bottom, "The Rock Stops Here.™", sliding bar, moving red pipeline line; built into the page head by `tools/build-pages.js`, `window.RGL.hold() / release()`) from the first paint until the CMS data is applied. It is not shown on the login page and the dashboard.
- `js/rg-cache.js` (`window.RGC`): first visit = loader; once the page is shown, the data of ALL pages (home, products, resources, project highlights, contact, lunch, credit) and lists (solutions, stories, resources, the page elements of every product) is fetched in the background and kept in the browser (localStorage). From then on every page is drawn at once from the cache (no loader, the page is only kept invisible for a few ms) and refreshed from the CMS in the background; entries older than 10 minutes are refreshed by the background fetch, the whole cache expires after 24 h. A page reload (F5 / Ctrl+R) clears the cache first (loader once, then cached again). A signed-in admin uses the cache too (loader once after the login, then no loader when switching pages until a reload): login clears it and sets a flag, SAVE refreshes the cache in the background (RGC.refresh), logout / dashboard logout clear it.
- Hooks: `js/cms.js` (`loadSaved`), `js/rg-content.js` (`get`), `js/login.js`, `js/dashboard.js` (logout).

## Scroll animations (`js/rg-motion.js`, `css/rg-motion.css`)
- **Every page** (home, products, resources, project highlights, contact, credit, lunch) **and every template page** (product, project, blog, webinar: so a page made later from a template has them too): the title banner plays an entrance (photo eases in with a soft zoom-out, small label, title slides in with a blur clearing, the rest rises), and while scrolling headings slide in, texts rise, photos unveil with a soft zoom, cards (products, features, resources, projects, questions, stats, offices) rise one after another; a thin red progress bar runs along the top. Banner text is held invisible from the first paint (`html.rgm-pre`, set in the head) so it never flashes, and the entrance starts when the page loader has gone.
- Only classes are added (no text is split or rewritten): text / photo changes of the live editor, lists drawn from the CMS (they are picked up by a MutationObserver; what is already on screen never hides and re-animates), the add / remove of list items and sections, and the template pages keep the same animation. In edit mode the scroll reveals stand still (so typing never flickers), the banner entrance is unchanged; "reduce motion" turns everything off.

## Mobile / tablet check
- Checked with a real Chrome (Playwright, local pages only) at 320 / 375 / 414 / 768 px for home, products, a product page, resources, project highlights, a project page, contact, lunch & learn and credit application: no horizontal scrolling anywhere, the hamburger menu opens / closes and the Support sub menu opens by tap, forms are single column, cards stack. Fixes made from that check (`css/site.css`): the Resources filter tabs are one swipeable row (they wrapped into scattered rows), the project page's challenge / solution box has phone padding and full width tabs.
- Edit mode (admin bar, toolbar) is designed for a computer screen.

## Cookie banner + Privacy Policy
First-visit banner (Accept / Deny / View preferences, Do Not Sell link, Global Privacy Control = deny), choice in localStorage rg_cookie_consent, reopened from footer "Cookie Preferences". privacy-policy.html covers cookies, storage, CMS login, ZoomInfo, forms, CCPA. ZoomInfo tag URL goes in ZOOMINFO_SRC in js/rg-consent.js.
